# 03 技术方案

> 目标：用**最低成本**做出可验证"红外学习 + 照明 + 定时 + 动作"的最小样机。
> 本文所有功耗、温升、扭矩、成本数字均可由 `tools/mvp_calc.py` 复现。
> 未标注来源的器件参数为**典型值/设计目标**，需在打样后实测修正。

---

## 一、设计目标与边界

### 1.1 硬性指标（Gate 1 验收）

| 指标 | 目标值 | 测量方法 |
|------|--------|----------|
| 红外学习成功率 | ≥ 90%（首次） | 5 品牌 × 30 次/品牌 |
| 红外发射距离 | ≥ 5 m，±30° 锥角内 | 卷尺 + 空调实际响应 |
| 照明照度 | ≥ 500 lx @ 40cm 中心 | 照度计 |
| 显色指数 | Ra ≥ 90 | 光谱仪（可委外） |
| 调光频闪 | 波动深度 < 5%，频率 ≥ 3 kHz | 示波器 + 光电二极管 |
| 外壳温升 | ≤ 45 K（满载 2 h） | 热电偶 |
| 学习模式待机噪声 | < 25 dB(A) @ 1m | 声级计 |
| 舵机动作噪声 | < 45 dB(A) @ 1m | 声级计（普通卧室背景约 30 dB） |
| 动作寿命 | ≥ 20,000 次 | 加速测试 |
| 断电后红外码保留 | 100%（写入完成即持久） | 断电 100 次抽测 |

### 1.2 明确不做的技术项（避免范围蔓延）

- 不做 WiFi 云端码库同步（首版）；不做手机 App；不做摄像头/坐姿识别；
- 不做全屋红外组网（一台一机）；不做电池供电（常插电）；
- 不做语音唤醒词识别之外的连续语音（LD3320 只做命令词）。

## 二、系统架构

```
                 ┌──────────────────────────────────────────────┐
                 │              ESP32-S3-WROOM-1                │
                 │  4MB Flash / 2MB PSRAM / WiFi+BLE            │
                 │                                              │
   按键 x3 ──────┤ GPIO  → 状态机（短按/长按/双击）             │
   OLED  ────────┤ I2C   → 表情 + 状态 + 倒计时                 │
   TSOP38238 ────┤ GPIO  → IRrecv（RMT 硬件捕获）                │
   IR LED x2 ────┤ GPIO  → IRsend（38kHz 载波，RMT 调制）        │
   LED 暖白 ─────┤ LEDC  → PWM 1（PT4115 DIM）                   │
   LED 冷白 ─────┤ LEDC  → PWM 2（PT4115 DIM）                   │
   舵机 点头 ────┤ LEDC  → PWM 3（50Hz，0.5–2.5ms）              │
   舵机 转向 ────┤ LEDC  → PWM 4（50Hz，0.5–2.5ms）              │
   蜂鸣器 ───────┤ LEDC  → PWM 5（4kHz 方波）                    │
   语音模块 ─────┤ UART1 → LD3320（9600bps，命令词 ID）           │
                 │                                              │
                 │  LittleFS：红外码库 / 配置 / 日志             │
                 │  NVS：定时任务 / 校准参数 / 使用计数          │
                 └──────────────────────────────────────────────┘
```

**为什么用单循环 + 非阻塞时基，而不是多任务**：
红外捕获由 RMT 硬件完成，不占用 CPU；照明/舵机/定时都是毫秒级周期任务。
单循环 + `millis()` 调度足以满足时序，且调试简单、无跨任务竞态。
只有在加入 WiFi OTA 与语音并发后再考虑 FreeRTOS 任务拆分（见 9.4）。

## 三、硬件选型

### 3.1 主控

| 候选 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| **ESP32-S3-WROOM-1-N4R2** | RMT 通道多（8 个），LEDC 8 通道，PSRAM 便于码库 | 单价略高 | **选用** |
| ESP32-C3 | 更便宜 | RMT 仅 2 通道、LEDC 6 通道，做双舵机+双路调光偏紧 | 备选（基础版降本） |
| ESP32-WROOM-32 | 生态成熟 | GPIO 与 RMT 资源略少，无 USB-OTG | 不选 |
| STM32F103 | 实时性好 | 无 WiFi，后续 OTA/配网需外挂 | 不选 |

**关键理由**：红外收发需要 RMT（精确到 1µs 级的载波与采样），
LED 双路调光 + 双舵机 + 蜂鸣器需要 5 个独立 PWM 通道。ESP32-S3 同时满足且留有余量。

### 3.2 关键器件与选型依据

| 功能 | 型号 | 关键参数 | 选型理由 | 单价 |
|------|------|----------|----------|------|
| 红外接收 | TSOP38238 | 38kHz，解调输出，±45°，≥25m | 内置前放与滤波，直接进 MCU | 2.2 |
| 红外发射 | 940nm 5mm IR LED ×2 | Vf 1.3V @ 100mA | 双管并联提升覆盖角 | 1.1×2 |
| 发射驱动 | 2N3904 / S8050 | Ic 200mA，Vce(sat) 0.2V | 低成本、足够驱动 120mA | 0.2 |
| 恒流驱动 | PT4115 ×2 | 1.2A，DIM 支持 PWM | 单路一路色温，抗电源波动 | 1.4×2 |
| 舵机（点头） | **MG90S**（金属齿） | 2.2 kg·cm @ 5V | 见 6.1 扭矩核算，SG90 余量不足 | 8.5 |
| 舵机（转向） | MG996R | 9.4 kg·cm @ 5V | 底座承重 | 14 |

### 3.4 可插拔红外模块接口定义（6 pin，2.54mm 排针）

| Pin | 信号 | 说明 |
|-----|------|------|
| 1 | 5V | 模块供电（发射瞬时 240mA，需 100µF 本地储能） |
| 2 | GND | — |
| 3 | IR_OUT | MCU → 模块，38kHz 已调制或裸脉冲（由模块 ID 决定） |
| 4 | IR_IN | 模块 → MCU，解调后基带信号 |

|-----|------|----------|------|------|

| 进阶 | 5V/2A | 900 mA（典型） | 55.0% | OK |
| 旗舰 | 5V/4A | 1646 mA（互锁后峰值） | 58.8% | OK |

### 4.1 电源设计的三个强制要求

1. **舵机互锁是电源预算的一部分**：两舵机同时堵转 + LED 满载 = 2846 mA，
   5V/4A 电源虽不烧，但线损会把电压拉到 4.6V 以下，导致 ESP32 复位（Brownout）。
   固件必须在运动前检查 `motion_busy`，并且**运动期间把 LED 目标亮度乘以 0.7**。
2. **舵机电源与 MCU 分开走线**：舵机地回流经 470µF 电解 + 100nF 陶瓷就地储能，
   星型接地到电源入口，不得穿过 MCU 地平面。
3. **红外发射瞬时电流**：240mA 脉冲会在 5V 轨上产生跌落，发射前 1ms 预充电（模块本地 100µF），
   否则 TSOP 会因电源抖动误判（表现为"自己发的码被自己收到"）。

### 4.2 关键电路参数计算

**红外 LED 限流电阻**（单管，5V 轨）：

```
R = (Vcc − Vf − Vce_sat) / I_peak
  = (5.0 − 1.3 − 0.2) / 0.120
  = 29.2 Ω   → 取标准值 27 Ω
P_R = I² × R = 0.12² × 27 = 0.39 W  → 选 1W 电阻（降额 40%）
```

载波占空比按 1/3 计，mark 期间平均电流 40 mA/管；一帧 NEC（约 67.5ms）实际导通 < 30ms，
平均电流 < 15 mA/管，对 5V/2A 电源无压力。

**TSOP38238 供电去耦**：100Ω 串联 + 0.1µF 到地（数据手册推荐），
抑制电源纹波导致的假触发；输出内部上拉，MCU 端配置为输入 + 内部上拉冗余。

## 五、红外子系统（本项目最核心的技术风险点）

### 5.1 为什么走"学习原始码"而不是"协议码库"

空调遥控器不是 NEC 那种"一个按键 32 位码"，而是**一次性下发完整状态**：
模式 + 温度 + 风速 + 扫风 + 定时，单帧常达 100–250 个 mark/space（约 200–600 字节原始数据），
且各家位定义完全不同（格力/美的/海尔/奥克斯/大金各不相同）。

| 方案 | 优点 | 致命问题 |
|------|------|----------|
| 内置协议码库（如 IRremoteESP8266 的空调类） | 无需学习，直接选型号 | 覆盖机型有限；新型号失效；维护成本高 |
| 协议解析 + 状态合成 | 可做"设定 26℃"这样的语义控制 | 需要逐品牌逆向，工期不可控 |
| **学习原始码（本项目）** | 任何遥控器都能学；零协议维护 | 只能"复现按键"，不能语义化；数据量大 |

**取舍**：MVP 只承诺"**按下你原来的按键，灯替你按一次**"，不做"把空调设到 26 度"。
这与用户真实需求（"我不想找遥控器"）高度一致，且把最大的技术不确定性移出了关键路径。
语义化控制作为 v2 的可选增强（需要 App 或语音 + 协议库）。

### 5.2 学习流程与时序

```
1. 用户长按 LEARN 3s      → 进入学习态，OLED 显示 slot 号，灯头轻点确认
2. irrecv.enableIRIn()    → RMT 开始捕获，超时 15s
3. 用户按遥控器            → IRrecv 解码/原始捕获
4. 校验：
   a. rawlen ∈ [20, 1024]          否则拒收（噪声/过短/过长）
   b. 重复捕获 2 次，两次差异 < 5%  否则提示"信号不稳，请靠近/换电池"
   c. 首尾 mark/space 合理性检查     否则拒收
5. 写入 LittleFS（先写 .tmp 再 rename，防掉电损坏）
6. 回读校验 CRC，蜂鸣 + 屏幕 "OK n"
7. 6 个键学完或超时 → 退出学习态，恢复照明
```

**重复捕获 2 次比对**是提升成功率的关键：单次捕获经常因电源抖动或手抖缺首码，
两次一致才存，能把"玄学失败"变成"明确提示用户重试"。

### 5.3 发射

```cpp
// 伪代码，实际见 firmware/src/ir_engine.cpp
irsend.sendRaw(raw, len, 38);   // 38kHz 载波由 RMT 硬件产生
```

- 每帧连发 **2 次**、间隔 40ms：空调多为单帧状态码，重复可显著提升首次响应率；
- 发射时先把 LED 亮度临时降 30%（避免电源跌落导致自身误收）；
- 发射后 100ms 内屏蔽接收（`irrecv.disableIRIn()`），防止自收。

### 5.4 存储格式（LIR1）

```
偏移  长度   字段
0     4     magic  'LIR1' (0x4C495231)
4     2     version = 1
6     2     freq_khz (38)
8     2     raw_len  (20..1024)
10    2     reserved = 0
12    2*n   raw[]    uint16 小端，mark/space 微秒
12+2n 4     crc32    覆盖 header+payload
```

**设计要点**：

| 决策 | 理由 |
|------|------|
| 存 LittleFS 文件，不存 NVS blob | NVS 单条 blob 建议 < 4KB 且碎片敏感；空调整帧 1.2KB，多槽位会撑爆分区 |
| 固定 16 字节头 + 定长 payload | 解析无需 JSON，节省 RAM；单条最大 2060 字节 |
| magic + version + CRC32 | 掉电半写、Flash 位翻转、旧版本固件都能被识别并拒绝，而不是发出乱码 |
| `.tmp` → `rename` 原子提交 | LittleFS rename 是原子的，避免"写一半"变成有效文件 |
| 槽位命名 `slot0..slot15` | 与按键映射解耦，允许一个槽位被多个按键引用 |

自检（`python tools/mvp_calc.py selftest`，9 项全通过）验证了：
NEC 帧往返、602 条空调帧往返、CRC 篡改拒绝、截断拒绝、超长拒绝、空记录拒绝、
最坏情况 16 槽 × 1024 条 = 32KB 可放入 1MB LittleFS 分区。

|------|------|----------|------|------|
| 格力 | 待填 | | | 状态码型 |

## 六、照明子系统

### 6.1 调光与色温

| 参数 | 取值 | 依据 |
|------|------|------|
| 双通道 | 3000K / 6000K 各 24 颗 2835 | 混光实现 2700–6500K |
| 驱动 | PT4115 ×2，恒流 350mA/通道 | 抗输入电压波动，无频闪 |
| PWM 频率 | 4 kHz | >1.25kHz 避开人眼与相机条纹；4kHz 兼顾 MOS 开关损耗 |
| PWM 分辨率 | 12 bit（4096 级） | 80MHz / 4kHz = 20000 ≥ 4096，可稳定输出 |
| 调光曲线 | Gamma 2.2 查表（256 项） | 线性 PWM 在低亮度段感知不平滑 |
| 最低亮度 | 1%（约 3 lx） | 夜间起夜可用，不刺眼 |

**混光公式**（色温目标 T，范围 2700–6500K）：

```
若 T ≤ 3000K: warm = 100%, cool = 0%
若 T ≥ 6000K: warm = 0%,   cool = 100%
否则: t = (T − 3000) / 3000
      warm = (1 − t) × brightness
      cool = t × brightness
```

> 注意：这不是 CCT 线性插值，实际色坐标会有偏差。MVP 阶段用
> **5 档预设**（2700/3500/4300/5200/6500K）实测校准每个预设的两路占空比，
> 比连续调色温更可靠。校准值存 NVS。

### 6.2 光学与结构

| 项 | 方案 | 目标 |
|----|------|------|
| 出光 | PMMA 扩散板 + 30° 遮光角 | 无眩光（UGR < 19） |
| 照度 | 40cm 处中心 ≥ 500 lx | 满足阅读/书写 |
| 均匀度 | 中心 50cm 内 ≥ 0.7 | 避免明暗分界 |
| 色容差 | SDCM ≤ 5 | 同批次灯珠分 bin |

### 6.3 热设计（计算器输出）

| 项 | 数值 |
|----|------|
| 电功率 | 5.0 W |
| 光效（估） | 30% |
| 发热 | 3.5 W |
| 散热器热阻 | 6.5 ℃/W（60×40×8mm 铝板，自然对流） |

## 七、机械动作子系统

### 7.1 扭矩核算（必须做，不能拍脑袋）

**点头轴（俯仰）**

```
灯头总成质量 m ≈ 0.18 kg（LED 板 + 散热器 + 扩散板 + 外壳）
重心到转轴距离 d ≈ 0.060 m
静态扭矩 T = m × g × d = 0.18 × 9.8 × 0.060 = 0.106 N·m ≈ 1.08 kg·cm
安全系数 1.5（摩擦 + 动态 + 齿轮间隙） → 需求 1.62 kg·cm
```

| 候选 | 堵转扭矩 | 余量 | 结论 |
|------|----------|------|------|
| SG90（塑料齿） | 1.8 kg·cm | +11% | **不足**，温升后扭矩下降，会点头点头停不住 |
| **MG90S（金属齿）** | 2.2 kg·cm | +36% | **选用** |
| MG996R | 9.4 kg·cm | +480% | 过重（55g）、噪声大，浪费成本 |

**转向轴（偏航）**

```
头部总成 + 悬臂 m ≈ 0.35 kg，重心偏置 d ≈ 0.040 m
T = 0.35 × 9.8 × 0.040 = 0.137 N·m ≈ 1.40 kg·cm
需求（×1.5）= 2.10 kg·cm
MG996R 9.4 kg·cm → 余量 348%，满足；可用 20% 占空比降速降噪
```

### 7.2 动作设计原则（防止"吵、抖、烦"）

| 原则 | 实现 |
|------|------|
| 无动作时舵机断电 | 到位后 `ledcWrite(ch, 0)` 停止 PWM，避免持续嗡嗡声与发热 |
| 缓动而非跳变 | 每 20ms 移动 1.5°，S 曲线（前 20% 加速、后 20% 减速） |
| 硬件限位 + 软件限位 | 机械挡块 + 固件角度范围（点头 10°–55°，转向 −60°–+60°） |
| 动作去重 | 同一提示 3 秒内不重复动作 |
| 夜间静音 | 22:00–07:00 只走灯光提示，不动作（可配置） |
| 手动优先 | 用户手扶灯头时，检测电流/角度异常立即释放（防堵转烧舵机） |
| 行为克制 | 单次提示 ≤ 2 个动作；连续提示间隔 ≥ 3 分钟 |

**噪声预算**：MG90S 空载约 35–40 dB(A) @ 1m，MG996R 约 45–50 dB(A)。
夜间静音模式是必须功能，否则第 3 天就会被用户关掉——这会直接摧毁"情绪价值"假设。

### 7.3 结构与寿命

| 项 | 要求 |
|----|------|
| 齿轮 | 金属齿（MG90S/MG996R 原厂或同级） |
| 轴系 | 铜套或双滚珠，间隙 < 0.1mm |
| 走线 | 舵机线过孔加护套，弯折寿命 ≥ 5 万次 |
| 寿命 | ≥ 20,000 次往复（约等于每天 10 次 × 5.5 年） |
| 失效模式 | 优先"齿轮打滑但不断电"，不允许卡死烧驱动 |

## 八、定时子系统

### 8.1 时间源策略（分层降级，必须写清楚）

| 优先级 | 时间源 | 精度 | 失效时行为 |
|--------|--------|------|------------|
| 1 | SNTP（WiFi 已配网） | ±100ms | 每天校时 1 次 |
| 2 | DS3231 RTC（可选，+2 元） | ±2ppm（月差 <1 分钟） | 主用，SNTP 仅校准 |
| 3 | `millis()` 累计 | 每日漂移 1–5 秒 | **只允许倒计时**，禁用"每日定时" |

**关键取舍**：不装 RTC、不联网时，**只提供倒计时（≤ 24h）**，
不提供"每天 8:00 开灯"这类绝对时间任务。因为漂移会让定时越来越不准，
用户会认为"这灯坏了"，而不是"没联网"。

### 8.2 任务模型

```c
typedef struct {
    uint8_t  id;          // 0..7
    uint8_t  type;        // 0=倒计时 1=每日 2=单次绝对时间
    uint8_t  days_mask;   // bit0..6 = 周一..周日（每日任务用）
    uint8_t  action;      // bitmask: 1=开灯 2=关灯 4=红外slot 8=动作提示
    uint16_t minute_of_day;  // 每日/绝对任务
    uint32_t duration_s;     // 倒计时
    uint16_t ir_slot;        // action & 4 时有效
    uint8_t  flags;       // bit0=启用 bit1=已触发(单次)
    uint32_t next_fire;   // 运行期计算，不持久化
} task_t;
```

**存储**：NVS blob，8 个任务 × 16 字节 = 128 字节，远低于 NVS 限制。
**掉电策略**：任务定义持久化；`next_fire` 重新计算；倒计时任务记录 `deadline_epoch`，
若断电期间已过期，则**触发一次**（而不是静默丢弃），并在屏幕提示"错过的提醒"。

### 8.3 防误触发

| 场景 | 处理 |
|------|------|
| 时间跳变（SNTP 校时一次跳 10 分钟） | 校时前后 2 秒内不判定任务触发 |
| 同一任务重复触发 | 触发后立即写 `last_fire`，60 秒内不重复 |
| 用户手动关灯 | 清除该任务的"开灯"动作，但不删除任务 |
| 夜间触发 | 仅灯光渐变 + 轻微提示音，不动作（见 7.2） |

## 九、语音子系统（旗舰版，第三轮才投入）

### 9.1 为什么选离线 LD3320 而不是云端 ASR

| 方案 | 延迟 | 依赖 | 成本 | 隐私 | 结论 |
|------|------|------|------|------|------|
| **LD3320 离线命令词** | < 500ms | 无 | 17 元 | 本地 | **选用** |
| ESP32-S3 + 云端 ASR | 1–3s | WiFi + 服务费 | 0（但需服务） | 上传音频 | 不做 |
| ESP-SR（ESP32-S3 本地唤醒词） | < 300ms | 无 | 0 | 本地 | v2 备选（需 8MB PSRAM 与模型调优） |

**理由**：产品只需要"开空调/关空调/调暗/定时 45 分钟"这类 20 条命令，
离线方案零网络依赖、零服务费、响应快，且失败时用户会改按按键，体验仍可接受。

### 9.2 命令词设计（20 条，必须两字以上、发音差异大）

| 分组 | 命令词 | 动作 |
|------|--------|------|
| 灯 | 开灯 / 关灯 / 亮一点 / 暗一点 / 学习模式 / 休息模式 | 照明 |
| 空调 | 开空调 / 关空调 / 调高温度 / 调低温度 | 红外 slot 0–3 |
| 定时 | 定时半小时 / 定时一小时 / 取消定时 | 倒计时 |
| 系统 | 安静模式 / 报告状态 | 动作/语音开关、OLED |

**禁用词**："开"（与"开灯/开空调"混淆）、"关"、"好"、"嗯"（易误触发）。

### 9.3 误唤醒抑制

- 必须"**唤醒词 + 命令**"或"**命令词 + 确认音**"二选一，不能裸命令直接执行；
- 置信度阈值可调（默认 0.65），低于阈值时灯头轻摆表示"没听清"，不执行；
- 电视/音箱播放人声是主要误触发源，需在实测中用真实电视节目做 2 小时误触发率测试，
  目标 < 1 次/小时。

## 十、固件架构

### 10.1 模块划分

```
firmware/src/
├── main.cpp          初始化、单循环调度、按键状态机
├── config.h          引脚、常量、编译期开关（见 include/config.h）
├── lighting.cpp      双通道 PWM、Gamma、预设、渐变
├── ir_store.cpp      LIR1 记录读写、CRC、原子提交、槽位管理
├── ir_engine.cpp     学习/校验/发射（IRremoteESP8266 封装）
├── timer_task.cpp    任务模型、时基、触发
├── motion.cpp        舵机缓动、限位、互锁、静音策略
└── ui.cpp            串口 CLI + OLED（可选编译）
```

### 10.2 主循环时基

```c
void loop() {
    uint32_t now = millis();
    button_poll(now);          // 每 5ms，非阻塞，去抖 20ms
    ir_poll(now);              // 每 5ms，调用 irrecv.decode()
    lighting_tick(now);        // 每 20ms，渐变插值
    motion_tick(now);          // 每 20ms，仅在运动时执行
    timer_tick(now);           // 每 250ms，检查任务
    ui_tick(now);              // 每 100ms，刷新 OLED/串口
    // 无 delay()，无阻塞等待
}
```

**为什么要严格非阻塞**：IRrecv 依赖高频轮询，任何 `delay(500)` 都会丢码，
表现为"学习成功率忽高忽低"。这是新手最常见的坑，代码评审必须检查。

### 10.3 存储布局

| 区域 | 用途 | 大小 |
|------|------|------|
| NVS | 定时任务、照明校准、使用计数、设备配置 | ~4KB |
| LittleFS `/ir/slotN.lir` | 红外码库（16 槽） | 最大 32KB |
| LittleFS `/ir/import/` | OTA 码库补丁 | ~64KB |
| LittleFS `/log/` | 最近 7 天使用日志（滚动） | ~32KB |
| OTA 分区 | 双分区 A/B | 各 ~2MB |

### 10.4 OTA 与码库补丁

- OTA 走 WiFi（`ArduinoOTA` 或 HTTP），带版本号与 SHA256 校验，失败自动回滚；
- **码库补丁**：厂商侧整理"机型 → 原始码"文件，用户通过串口/小程序写入 `/ir/import/`，
  固件在启动时校验并合入槽位。这是把"学不会"从退货转为软件问题的关键机制。
- 必须保留**串口 CLI**（`learn 3` / `send 3` / `status`），售后排查全靠它，
  且是自动化测试的入口。

### 10.5 使用日志（验证期的核心数据）

```c
// 每次事件写一行，掉电不丢（先写缓冲，30 秒批量落盘）
{"t": 137, "ev": "ir_send", "slot": 0, "ok": 1}
{"t": 180, "ev": "learn_result", "slot": 2, "ok": 0, "reason": "unstable"}
{"t": 900, "ev": "timer_fire", "id": 1, "action": 5}
{"t": 1200, "ev": "motion", "type": "nod", "muted": 0}
```

**为什么重要**：Gate 3/Gate 4 的"红外周使用 ≥ 3 次/人""动作是否被关掉"
必须靠设备日志回答，不能靠用户回忆。日志字段在 MVP 第一版就要埋好，否则后期补不回来。

### 11.3 三个最可能出问题的地方（提前埋点）

1. **红外发射功率不足**：用户放得远（>5m）或角度偏 → 表现为"学得会但空调不理"。
   对策：双管并联 + 27Ω 限流 + 发射时降灯光；售后手册第一条就是"把灯头对准空调"。
2. **舵机堵转烧驱动**：用户手掰灯头 → 电流飙升。对策：舵机电源串 0.5A 自恢复保险丝，
   并在固件中检测"连续 N 次未到位"即释放 PWM。
3. **WiFi 配网失败导致反复重启**：SNTP 阻塞或 DHCP 超时。对策：WiFi 连接全程非阻塞，
   15 秒未连上就进入离线模式（红外/照明/定时全部可用），**不重启**。

## 十三、技术方案自检清单（每次改设计都过一遍）

- [ ] 新增外设是否占用 strapping 引脚（0/3/45/46）或 Flash 引脚（26–32）？

- [ ] 新任务类型是否在断电/校时/手动干预下都不会误触发或重复触发？
- [ ] 主循环里是否引入了任何 `delay()` 或阻塞式网络调用？
- [ ] 新增功能是否会增加夜间噪声或光污染？夜间模式是否需要覆盖？
- [ ] 用户能否在没有 App、没有网络的情况下完成主要流程？
